## R01：来源与版本保护

目标：先让当前成果有可审查、可恢复的基线。状态：计划中，未开启。

1. Codex 在获准范围查找原仓库线索和交付来源；不能根据目录名猜测远端。用户只补充工程中找不到的来源事实，不承担 Git 操作。
2. 对源码、历史 APK、测试、文档和设计资产登记清单及校验。准备持久保护副本，排除凭据、签名私钥和真实用户数据；本机配置原位保留。检查范围和空间后再确定副本位置，不把本轮临时证据目录当备份。
3. 若找到原仓库，先比较现目录与原基线，保护差异后再提出接续方案；若确实无原仓库，提交具体的新仓库方案供用户批准，不擅自初始化。
4. 获准后由 Codex 配置最小忽略规则和本地版本基线，明确排除 local.properties、缓存、生成文件、密钥及用户数据。历史 APK 另登记保留位置，不能因忽略或归档而删除原件。逐项审查拟纳入文件，不能用全量暂存代替检查。
5. 验证受保护文件可恢复到隔离位置、身份与资产校验不变；记录仓库/提交、来源关系和未纳入项。提交、分支、远端或推送操作须符合用户明确授权，不自动进行。

验收：版本来源明确或明确记为无法追溯；当前成果有持久且经过恢复核对的保护；不会提交敏感文件；后续会话能定位基线。Git 不是用户数据备份，恢复业务数据仍需 R03。

回退：只撤销本阶段新建且无后续写入的保护配置或元数据，不覆盖原文件，不删除原仓库或唯一备份。

## R02：可重现质量基线

目标：区分软件问题与环境问题。状态：计划中，未开启。

1. 从 R01 可追溯源码创建隔离副本，不复制 local.properties、旧 build/.gradle/.kotlin、真实数据或签名私钥；不清理原目录缓存。
2. 核对 JDK、SDK、Gradle 8.9 和现有离线缓存；先用 [quality](../quality.md) 的构建/Lint 命令，不升级工具链，不因缺少缓存自行安装依赖。
3. 使用同一次新构建生成的类与 schema 运行当前有效回归。先复核 `test_room_migration_v6.py` 的重复列风险；获准修改测试后再作最小修复并验证，不把测试失败混成产品已损坏或已通过。
4. 记录全部通过/失败/未执行/环境受阻及报告；对 Lint 警告逐项区分现有与新增，评估依赖 TLS 警告的可达性，不顺手升级依赖或屏蔽规则。
5. 记录源码与新 APK 对应、版本及哈希；核对历史 APK 签名连续性只读取公有证书信息，不读取私钥。在线 API、真机体验和完整数据升级另列待验收。

验收：可从明确源码在隔离目录重现构建、Lint 和有效回归；失败有归因与后续任务，生成类不混用。不能用历史 M01 或 v0.2.1 通过记录代替本次全套基线。

回退：只处理明确的新隔离产物，不触碰原目录和用户数据；保留失败摘要以便接手。

## R03：数据与核心体验保障

目标：优先覆盖数据丢失和日常编辑/聊天风险。状态：计划中，未开启；测试与代码变更均需实施授权。

- 建立可重建的合成测试资料：笔记、同名双链、项目/文件夹、会话、草稿、历史版本、附件和上下文。不得复制真实资料作测试夹具。
- 明确代码登记的 1→8 迁移与业务备份接受 databaseVersion 6—8、归档 format version 1 的区别；登记可验证版本和缺失历史证据，不伪造旧库。补齐受支持升级链、旧备份、恢复失败回滚及附件完整性测试，保留所有旧迁移。
- 复核删除/清理、项目记忆、同名和改名链接的一致性；先建立能揭示问题的测试，再在明确范围修复。禁止破坏性重建数据库解决升级问题。
- 使用无真实数据的模拟器/设备验证中文 IME、emoji、选区、撤销/重做、自动保存、收键盘、项目切换、草稿及进程恢复。启动前确认目标和数据隔离。
- 用测试归档演练导出与恢复，比较记录及附件校验；应用自有备份不含 API 配置。真实数据操作或安装覆盖用户现有应用，必须先单独提出风险与可恢复方案并获准。
- 在线调用仅在用户批准供应商/模型和费用范围后进行，不输出 Key。未授权不影响离线与合成数据工作。

验收：按质量矩阵保存场景、断言、实际结果及限制；备份恢复和升级有可重复证据，核心体验由用户最终验收。未覆盖的版本/设备明确保留为未确认。

回退：仅测试副本可重建；若将来调整数据格式，必须先有独立保护与兼容方案，不能假定降级安装能恢复数据库。

## R04：日常检查自动化

目标：把已经稳定的命令变成可重复执行的最小入口。状态：计划中，未开启。

1. 复用现有 Shell/Python/Gradle 提供文档检查、按范围回归和完整基线的入口，检查环境缺失时清晰失败并保留结果；不引入新的任务平台。
2. 入口区分只读检查与生成产物，不启动生产应用、不读取真实凭据、不恢复真实数据；明确运行目录、前提及退出状态。
3. 版本来源、远端和执行环境确定后再评估 CI；优先复用同一入口，敏感信息不写入配置。不为建立 CI 自动开账号、接远端、推送或发布。
4. 校验入口能揭示失败、每个必要套件确实执行；将执行证据和后续会话用法同步到 quality，替换过期说明时保留历史语境。

验收：新会话按项目文件由 Codex 完成检查并解释结果；入口不会将缺环境或跳过套件记为通过；版本操作有可回退基线。CI 未选定时明确标记未建立，不阻碍先完成本地入口。

## R05：按需求渐进整理

状态：计划中，未开启。只有具体需求或已经证实的维护问题触发，不把搬目录当成果。

- 保持现有栈和单模块，一次整理一条已有行为链路；先有回归，再考虑职责拆分。
- DshApp 的聊天、草稿和项目切换共同评审；Entity/DAO/迁移/备份和编辑器/保存/版本恢复分别保持整体兼容验证。
- 设计原图、资源 ID、应用身份、历史 APK 与备份边界继续保护；额外资产迁移不是重启必选项。既有 M01 成果原位保留。
- 产品变化同步 product，职责变化同步 ARCHITECTURE，验证变化同步 quality；实际兼容/技术决定写 ADR。

验收：明确需求得到满足、原行为回归无退化、集成后验证通过；是否增加模块或依赖有具体收益和决定记录。
