按本次用户意图选择项目级 Skill：[需求整理](../.agents/skills/intake/SKILL.md)、[技术研究](../.agents/skills/research/SKILL.md)、[新功能实施](../.agents/skills/feature/SKILL.md)、[故障修复](../.agents/skills/bugfix/SKILL.md)、[独立检查](../.agents/skills/review/SKILL.md)。需求确认与实施授权分别核对；Skill 不改变当前阶段或高风险操作的授权边界。

## 每次开工

1. 读 AGENTS、[当前状态](current-state.md)、[架构](../ARCHITECTURE.md)、[产品边界](product.md)，再读 [任务索引](exec-plans/README.md)、目标任务和 [质量规则](quality.md)。涉及设计或持久化时补读 [资产](assets.md) 和 [决策](decisions/README.md)。
2. 核对当前目录与任务允许范围。由 Codex 查询 `git status --short --branch`；有仓库时核对分支、提交基线、已暂存和未暂存差异，无仓库时明确记录，未经授权不初始化。不得为获得“干净状态”而执行覆盖、reset、clean、stash 或删除。
3. 在任务文件登记目标、验收条件、允许/排除文件、负责人、起始状态和本次授权。授权描述引用用户原意；已有文档中声称的历史批准只能作历史记录。用户已授权的常规操作不重复索要批准。
4. 识别现有修改与并行任务。保存拟改文档的前副本；代码阶段按重启计划先取得可追溯源码保护。未知修改不能推定为自己或用户的成果；保持原状，收缩范围继续不重叠工作。
5. 把任务标为「进行中」并说明下一步。只推进用户已授权的任务范围；计划不会自行扩展授权。本次多个工程基础阶段已获准，必要常规操作不重复询问。

## 任务如何拆分与流转

每次只解决一个可以独立验收的问题。小任务直接用一份 Markdown 记录，不引入工单平台或额外框架。重启任务用 R 编号；后续任务可用 `T-YYYYMMDD-简短名称.md`，先查重再建文件。

真实需求整理和独立审查本身是可交付任务，即使尚未授权业务实施，也应按相应 Skill 保存记录并更新索引；索引中“开始实施某任务”包括开始执行这些非业务任务，不表示业务开发获准。用户明确要求仅做模拟演练且不创建正式任务时，模拟需求、故障和审查不进入正式任务索引；将演练结论和必要交接保存到合适的既有工作流文档或实际授权的演练记录中，清楚标记为模拟，不冒充产品事实、用户确认或执行证据。

状态统一为「计划中 → 进行中 → 待验收 → 完成」。需要用户决定则写「待决定」，环境或来源阻塞则写「受阻」，记录恢复条件。技术验证和用户体验验收分别记录；不能把构建成功当作用户已验收。纯工程文档可在约定检查通过后完成，不据此声称软件质量基线完成。

变更前写出最小步骤、受影响链路、验证选择和回退方式。新发现超出范围的问题登记到任务，不顺手修复；只有确认属于当前需求的必要修复才纳入，并更新验收范围。

## 多会话和集成

- 默认同一目录串行写入。任务索引中登记负责人和占用路径；这只是协作约定，不是文件系统锁，也不能防止未遵守规则的会话同时写入。
- 需要并行开发时，先明确各任务范围和集成人；版本保护建立后，由 Codex 在已授权范围创建独立分支/工作区。Git 尚未建立前，共享目录不并行写代码；隔离副本结果只作为候选，不能整目录覆盖主目录。
- `DshApp.kt` 是聊天/草稿/项目切换的共同编排点；Entity、DAO、迁移、备份是同一兼容链；编辑器、保存与版本恢复是另一条链。即使文件不同，涉及同一行为也先协调，避免只按目录分工。
- 工作会话交付文件差异、测试证据及未解决事项。集成人检查主目录是否产生新修改，逐项审查冲突；不自动选“全部采用某一方”，不覆盖未知修改。实质冲突解决后重跑受影响检查。
- 本次已授权建立并提交本地工程基线。其他任务未明确授权时不自动提交、切换分支；不自动推送或发布。版本操作只处理本任务明确文件，禁止不审查就全量暂存；记录提交标识和验证依据。合并后的最终源码才是验收对象，分支通过不能替代集成验证。

## 验证与完成

先由 Codex 运行 `python3 tools/check.py quick`，再按 [质量矩阵](quality.md#按变更选择检查) 选检查。首次基线、检查入口或回归体系变化用 `python3 tools/check.py baseline` 在全新隔离副本执行。每条结果记录日期、源码基线、工作目录、环境前提、实际命令、退出结果、报告位置和覆盖限制；状态使用「通过 / 失败 / 未执行 / 环境受阻」。旧报告、旧编译类、演示截图不得替代当前执行证据。

文档变更核对链接、状态和版本并检查空白；业务改动补充与风险相称的回归，不写只重复实现的测试。无法执行的必要检查保留为未验证项，不能勾选相应验收。发现可能造成数据丢失的失败时停止集成，保留现场。

完成前由 Codex 检查最终差异及保护文件，更新任务状态与证据；仅当事实变化时更新 current-state、product、ARCHITECTURE、quality 或 assets。实际长期技术决定才写 ADR，不为每次小改动新建决策。

## 中断或结束时的最小交接

交接写入任务文件，不仅留在回复中：

- 已完成和未完成；本次允许范围与明确未授权部分。
- 修改文件、起始/结束基线；有 Git 则记录分支和提交，无 Git 则记录哈希或差异副本位置及限制。
- 实际验证结果、失败原因、尚未验证的设备/在线/数据场景。
- 下一条可直接执行的动作、前置条件和回退范围。
- 负责人是否已停止写入，是否仍有构建/服务进程；没有运行也明确写明。

临时路径只保存排查证据，不承诺长期存在；关键结论和必要摘要必须在任务文件中。接手会话先重新核对磁盘状态，不盲信上次状态或过期的任务占用记录，不擅自接管可能仍在写入的任务。

面向用户的结束说明固定覆盖四件事：完成了什么、实际验证到哪一步、对已有功能的影响、需要用户决定什么。技术操作由 Codex 执行，用户不需要手动敲命令或搬文件。
